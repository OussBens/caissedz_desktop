Passage en client-serveur

CaisseDZ Desktop sur plusieurs PC d'un même réseau local (LAN) : plan d'action, temps et modifications. Document de travail : les changements de plan se font ici (voir le journal en bas).

Version du document : 3 · 30/10/2026 Application : CaisseDZ Desktop 0.5.3 Durée estimée : ≈ 9 semaines (première version utilisable ≈ 6,5)

0En bref

Un PC devient le « poste principal » : c'est lui le serveur. Les autres PC du magasin s'y connectent sur le réseau local et travaillent en même temps sur les mêmes données (stock, ventes, clients, caisses).

  • Pas de XAMPP, pas de MySQL, rien d'autre à installer. Le serveur est déjà dans CaisseDZ : la base reste le fichier SQLite chiffré du poste principal, et le petit serveur réseau qui sert aujourd'hui les téléphones (CaisseDZ Scan, port 8787) sert aussi les autres PC.
  • Un seul installeur pour tous les PC. Au premier lancement : « Ce PC est le poste principal » ou « Rejoindre le poste principal » (trouvé tout seul sur le réseau).
  • Le code de l'application change peu : tout le SQL passe déjà par les repositories. Sur un poste client, ces repositories parlent à la base du poste principal au lieu d'une base locale.
  • Basic ne change pas (un PC seul). Le réseau concerne Advanced et Max.

1Les trois offres et le réseau

Basic

1 magasin · 1 caisse · 1 PC

Comme aujourd'hui : un PC autonome, sa propre base. La caisse système et le magasin système sont fixes ; pas de coffre, pas de poste client.

Advanced

1 magasin · jusqu'à 5 caisses · jusqu'à 5 PC

Le poste principal + jusqu'à 4 postes clients dans le même magasin. Chaque PC est une caisse ; tous vendent en même temps sur le même stock.

Max

jusqu'à 15 magasins · 15 caisses · 15 PC

Plusieurs magasins et plusieurs caisses, transferts entre magasins et entre caisses. Tous les PC sur le même réseau (voir la décision D1 pour des magasins éloignés).

3L'architecture cible

Ce qui reste sur le poste principal

  • La base chiffrée, les sauvegardes, la restauration.
  • La licence BENS et le check-in (les postes clients la reçoivent du principal).
  • Le catalogue BENS, la tendance, Smart Scan, les téléphones.
  • L'heure de référence (dates des ventes, clôtures Z scellées).

Ce qui reste sur chaque PC

  • L'écran, les paniers en cours, la caisse du poste.
  • L'imprimante de tickets, le tiroir, la douchette, le format du ticket.
  • Les exports Excel / PDF enregistrés sur ce PC.
  • La langue et le thème de l’écran.

4Comment un poste client parle au poste principal

Aujourd'hui, tout le SQL est dans 28 repositories (lib/data/) qui reçoivent une base SQLite ; les 33 services (lib/application/) écrivent en une transaction. Réécrire ces quelque 330 accès en API REST prendrait des mois. Le plan garde ce code tel quel, en deux temps :

Étape A · la base à distance

Un objet BaseDistante se comporte comme la base SQLite (query, insert, update, transaction…) mais envoie chaque requête au poste principal par une connexion WebSocket. Le poste principal l'exécute sur la vraie base et renvoie le résultat.

  • Une transaction d'un poste client est tenue par le principal jusqu'au commit (rollback automatique si le PC se déconnecte ou après 10 s).
  • Après chaque écriture, le principal annonce les tables touchées à tous les postes, qui rafraîchissent leurs écrans.
  • Sur un réseau local, une requête prend environ 1 ms : un encaissement reste instantané.

Étape B · les écritures sensibles sur le principal

Les opérations qui comptent le plus sont exécutées entièrement par le poste principal, en une seule demande : le poste client envoie « encaisser ce panier » et reçoit la vente.

  • VenteService.encaisser, annulation et modification de vente, retours.
  • Ouverture et clôture de session, clôture Z (scellement SHA-256).
  • Achats, versements, transferts.

Moins d'allers-retours, aucune transaction ouverte à distance pour ces cas, et un contrôle des droits fait par le serveur.

Stock juste entre caisses. Deux caisses qui vendent le dernier article en même temps : la vérification du stock et l'écriture se font dans la même transaction sur la seule base. La seconde vente trouve le stock à zéro et reçoit « Stock insuffisant ». Pas de double vente.

7Le détail des phases

P0 · Renommer Ultra en Max

Fait½ jour
  • Palier NiveauLicence.max, libellés FR / AR / EN « Max », tests et documentation.
  • À faire côté bens_ds (autre dépôt) : renommer l'offre affichée « Ultra » en « Max » dans le tableau de bord et la page des offres ; les codes DSK-ULTRA… restent.

P1 · Fondations

En cours1 semaine
  • Accès aux données par une interface : appDatabaseProvider fournit soit la base locale, soit (plus tard) la base distante ; aucun repository ne change.
  • Réglages du poste : l'imprimante (imprimante_type, imprimante_adresse, imprimante_largeur), la douchette et le format du ticket quittent la table parametre partagée pour un fichier local du PC. Les réglages de la boutique restent en base.
  • Horloge : une Horloge unique remplace DateTime.now() dans les services ; sur un poste client elle suit l'heure du principal (ventes, sessions, clôtures).
  • Base prête pour plusieurs écrivains : WAL (déjà actif) + busy_timeout.
  • Identité du poste : code PST… tiré du code machine (déjà utilisé par la licence).

Livrable : l'application fonctionne exactement comme avant, prête à être branchée sur le réseau.

Fichiers : lib/core/db/app_database.dart, lib/app/providers.dart, lib/application/parametres_service.dart, lib/core/print/, services qui datent les opérations.

P2 · Serveur de données (poste principal)

À faire1,5 semaine
  • Étendre le serveur réseau existant (lib/application/serveur_mobile.dart, port 8787) d'une route WebSocket /api/v1/donnees réservée aux postes appairés.
  • Messages : requête, écriture, début / validation / annulation de transaction, lot ; une transaction distante à la fois sur la base, file d'attente pour les autres, annulation après 10 s ou à la déconnexion.
  • Annonce des changements : après chaque validation, les tables touchées sont envoyées à tous les postes.
  • Contrôle de version : un poste d'une autre version de l'application ou du schéma est refusé.
  • Table poste (code, nom, caisse, jeton haché, dernière connexion), comme appareil_mobile.

Livrable : le poste principal accepte des postes clients authentifiés et exécute leurs requêtes.

Nouveaux : lib/application/serveur_donnees.dart, migration v047 (table poste).

P3 · Poste client

À faire2 semaines
  • BaseDistante : la même interface que la base SQLite, au-dessus de la connexion WebSocket.
  • Rafraîchissement : chaque annonce de changement incrémente les compteurs de version des écrans concernés (stockVersionProvider, caisseVersionProvider…, déjà présents).
  • Écran « Connexion au poste principal » : liste des principaux trouvés, code d'appairage.
  • Bandeau « Poste principal injoignable », reconnexion automatique ; les paniers en cours sont gardés, rien n'est encaissé tant que le principal ne répond pas.
  • Désactiver sur un poste client ce qui n'a de sens que sur le principal : sauvegarde, restauration, compte BENS, téléphones.

Livrable : deux PC vendent en même temps sur le même stock.

Nouveaux : lib/core/reseau/base_distante.dart, lib/features/connexion_poste/.

P4 · Postes, caisses et licence

À faire1 semaine
  • Connexion sur chaque PC : l'utilisateur se connecte avec son propre compte (identifiant et mot de passe), sur n'importe quel PC. Les comptes, rôles, caisses et magasins attribués sont sur le poste principal.
  • N'importe quelle caisse sur n'importe quel PC : une caisse n'est pas attachée à un PC. L'utilisateur ouvre une de ses caisses attribuées (l'Admin : n'importe laquelle) sur le PC où il se trouve.
  • Une caisse ouverte reste sur son PC jusqu'à la clôture de sa session : ailleurs elle apparaît « En cours sur PC-2 » et ne s'ouvre pas (un tiroir, un comptage). Clôturée, elle redevient libre pour tous les PC.
  • Le PC propose la dernière caisse utilisée sur ce poste ; l'utilisateur en choisit une autre parmi les siennes.
  • Le matériel (imprimante, tiroir, douchette) suit le PC, pas la caisse.
  • PC en panne avec une caisse ouverte : l'Admin clôture la session depuis Gestion caisse, sur n'importe quel PC.
  • Limite de postes clients : Basic 0 ; Advanced 4 (5 PC avec le principal) ; Max 14 (15 PC). Un poste client de trop est refusé à l'appairage ; les téléphones CaisseDZ Scan ne comptent pas.
  • La licence est vérifiée sur le principal et transmise aux postes (lecture seule, fin d'essai, palier).
  • Écran « Postes connectés » dans Paramètres : nom, caisse, état, dernière connexion, Déconnecter.

Livrable : les limites des offres s'appliquent aux PC.

P5 · Installation automatique

À faire1 semaine
  • Installeur Inno Setup : règle du pare-feu (netsh advfirewall, réseau privé), lancement au démarrage de Windows pour le poste principal.
  • Annonce et découverte du principal sur le réseau (UDP), sans adresse IP à saisir.
  • Assistant du premier lancement : poste principal ou poste client.
  • Icône dans la zone de notification : le serveur continue quand la fenêtre est fermée.
  • Mise à jour des postes clients depuis le poste principal.

Livrable : installer et cliquer suffisent, sur chaque PC.

Fichiers : installer/caissedz.iss, lib/features/configuration/, windows/runner/.

P6 · Écritures sensibles sur le principal (étape B)

À faire1,5 semaine
  • Appels de service distants : encaisser, annuler, modifier une vente ; retour ; ouvrir / clôturer une session ; clôture Z ; achat ; versement ; transferts.
  • Droits vérifiés par le serveur (utilisateur, rôle, palier).
  • Limiter l'accès SQL direct des postes aux lectures et aux écritures simples.

Livrable : les opérations d'argent et de stock ne dépendent plus du réseau pendant leur transaction.

P7 · Tests et recette

À faire1 semaine
  • Tests automatiques : deux postes simulés vendent le même produit, coupure au milieu d'une transaction, reconnexion, version différente refusée.
  • Recette sur 3 PC réels (un principal, deux clients), Wi-Fi et câble, imprimantes différentes.
  • Mesures : temps d'un encaissement, d'une recherche produit, d'une liste de 5 000 produits.
