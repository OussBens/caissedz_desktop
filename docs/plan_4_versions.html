CaisseDZ Desktop : plan des 4 offres

Comment passer de la version actuelle (0.5.2) aux offres Basique, Avancé, Max et Cloud : changements, nouveautés, migration. Document de travail, 30/10/2026.

1. Les 4 offres visées

1 · Basique

Un poste, tout figé

  • 1 magasin système MAG0000
  • 1 caisse système CIS0000
  • Pas de création de caisse ni de magasin
  • Aucun transfert
Réseau : aucun (poste autonome)
2 · Avancé

Plusieurs caisses

  • 1 magasin figé MAG0000
  • Création de plusieurs caisses
  • Transferts entre caisses
  • Plusieurs postes
Réseau : LAN client-serveur
3 · Max

Plusieurs magasins

  • Tout l'Avancé
  • Création de plusieurs magasins
  • Transferts entre magasins et entre caisses
Réseau : LAN client-serveur, sans Internet
4 · Cloud

Gestion à distance

  • Tout le Max
  • Base de données dans le cloud
  • Connexion depuis n'importe où
  • Magasins sur des sites différents
Réseau : Internet (WAN)

4. Architecture cible

Le même logiciel fonctionne dans 3 modes. Le code métier (application/, data/) ne s'exécute qu'à un seul endroit : là où se trouve la base.

Poste client

Écrans identiques à aujourd'hui. Les lectures et écritures passent par l'API au lieu du SQL. L'imprimante, le tiroir et le scanner restent branchés en local.

Serveur

Seul endroit qui écrit dans la base : numéros de ticket, stock, scellement SHA-256, une transaction par opération. Il prévient les postes des changements par WebSocket.

5. Plan d'action par lots

0

Préparer les offres (sans réseau)

  • Renommer le palier ultra en Max, ajouter le palier Cloud (index 3) dans NiveauLicence et dans le produit de licence signée.
  • Regrouper les droits en un seul endroit : peut créer une caisse ou un magasin, transferts caisse / magasin, type de réseau (aucun / LAN / cloud).
  • Appliquer ces droits dans les services et pas seulement en masquant les boutons. Exemple : en Basique, la création de caisse est refusée même si on la demande par l'API.
  • Basique : CIS0000 et MAG0000 verrouillés. Avancé : magasin verrouillé, caisses libres dans la limite.
  • Corriger le dossier com.example, avec copie automatique des données existantes.
Livrable : version 0.6, toujours sur un seul poste, offres conformes.
1

Socle client-serveur

  • Une couche d'accès à double implémentation : locale (SQL actuel) et distante (appels API). Les écrans ne changent pas.
  • Choix du mode au premier lancement : Autonome, Serveur ou Client. Le choix proposé dépend de l'offre.
  • Migration de la base : table poste (nom, magasin, jeton, dernier contact) et code du poste sur les ventes et sessions de caisse.
Livrable : l'application marche comme avant en mode Autonome ; le socle est prêt.
2

Serveur LAN (Avancé et Max)

  • Étendre serveur_mobile.dart en API complète versionnée (/api/v1) : ventes, stock, achats, tiers, caisses, documents, paramètres.
  • Notifications en temps réel (WebSocket) à partir de l'existant DomaineMobile.
  • Démarrage automatique du serveur, règle de pare-feu ajoutée par l'installateur, IP fixe conseillée.
  • Écran « Postes connectés » : appairer, renommer, révoquer. Le nombre de postes est fixé par la licence (une seule licence, sur le serveur).
  • Sauvegarde automatique faite sur le serveur uniquement.
Livrable : un PC serveur auquel l'appli mobile se connecte toujours.
3

Poste client desktop

  • Découverte automatique du serveur sur le réseau, appairage par QR code ou par code.
  • Tous les écrans branchés sur l'API ; une session de caisse ouverte par poste.
  • Impression ticket et tiroir sur le poste client.
  • Serveur injoignable : bandeau d'alerte, vente bloquée, consultation possible, reconnexion automatique.
Livrable : offre Avancé client-serveur complète.
4

Max multi-magasins en LAN

  • Chaque poste rattaché à un magasin ; chaque utilisateur limité à ses magasins autorisés.
  • Transferts entre magasins (TRM) depuis n'importe quel poste, avec un stock juste partout.
  • Rapports consolidés tous magasins pour l'administrateur.
Livrable : offre Max. Recette à 3 PC minimum, coupure réseau, redémarrage du serveur.
5

Cloud

  • Le même serveur déployé en ligne (infrastructure bensds), HTTPS obligatoire.
  • Une base par client. Pour la V1, une base SQLite par compte : on réutilise tout le SQL existant. On pourra passer à PostgreSQL plus tard si le volume l'exige.
  • Comptes en ligne liés à la licence : connexion par identifiant + mot de passe, appareils approuvés, révocation à distance.
  • Sauvegardes quotidiennes chiffrées, journal des connexions.
Livrable : offre Cloud, connexion depuis n'importe où.
6

Hors ligne et synchronisation (surtout Cloud)

  • Avec les coupures d'Internet, un magasin doit pouvoir continuer à vendre.
  • Numéros de ticket réservés par poste (exemple TK-P02-000123) pour éviter les doublons.
  • File d'attente des ventes sur le poste, envoi automatique au retour du réseau, alerte si le stock devient négatif.
Livrable : Cloud utilisable en conditions réelles. Option possible pour le LAN.

6. Migration depuis la version actuelle

  1. Licences existantes conservées : Basic → Basique, Avancé → Avancé, Ultra → Max (même numéro de palier, aucune nouvelle clé).
  2. Mise à jour par-dessus : l'installateur remplace le programme ; la base caissedz.db reste en place.
  3. Sauvegarde automatique avant migration, puis migrations SQL au démarrage (nouvelles tables poste…). Aucune donnée perdue.
  4. Dossier de données : copie automatique de com.example\caissedz_desktop vers le nouveau dossier CaisseDZ.
  5. Avancé / Max : un assistant détecte « ce PC a déjà des données » et propose d'en faire le Serveur. Les autres PC sont installés en mode Client.
  6. Autres PC qui avaient déjà leur propre base : pas de fusion automatique (risque de doublons de tickets et de stock). Import ciblé des produits et clients, ou archivage de l'ancienne base.
  7. Passage au Cloud : bouton « Envoyer ma base vers le cloud ». La base est déchiffrée avec la clé du PC, re-chiffrée avec la clé du compte, puis envoyée ; le PC devient un poste client.
  8. Appli mobile : reste compatible (même appairage, API /api/v1).
